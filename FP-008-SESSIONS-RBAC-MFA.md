**Status:** ✅ DONE_LOCAL (backend) — приёмка выполнена и проверена локально; экранов MFA/OIDC/сессий в вебе нет; не выкладывалось
**Date:** 2026-10-30

Ночная версия FP-008 (`29d5f89`, `f366750`) откачена 30.10 (`5f86019`). Это новая реализация, 5 шагов.

## 8a. Сессии: отзыв и срок действия

Было: access-токен на 7 дней, выход отзывал только refresh-токен — украденный или «вышедший» access-токен работал до недели;
refresh-токены лежали в БД открытым текстом.

- Каждый вход открывает `auth_sessions`; access-токен несёт `sid`, живёт **15 минут** и принимается, только пока сессия
  не отозвана и не истекла (проверка в `JwtStrategy` на каждый запрос). Токены без `sid` (выданы до FP-008) — 401.
- Refresh-токен — в БД только **sha256**; ротация при каждом обновлении (условное обновление: из двух одновременных
  выигрывает одно); **повтор уже заменённого токена отзывает всю сессию** (`REFRESH_REUSE`).
- Выход, смена пароля, отключение пользователя — сессии отзываются сразу. Свои сессии: список, завершение одной,
  «выйти на остальных». Администратор организации — завершить все сессии пользователя.
- После выкладки все входят заново.

## 8b. Права (grants) и область из сессии

Было: старые модули (каталог, склады, торговля, касса, HR, аналитика, пользователи, роли, обмен) пускали любого
вошедшего в его организацию; можно было создать пользователя с любой ролью, подключить 1С; `OrgGuard` делал
владельцем любого с ролью `admin` в токене; `POST /roles` создавал глобальную роль для всех клиентов.

- Все старые контроллеры — через `OrgGuard` + `@RequirePermission` на каждый метод. **Организация — из
  `X-Organization-Id` (или своя), доступ — по активному членству в ней, права — по роли членства.** Права в
  разных организациях у одного пользователя разные.
- Новые права: `catalog.read/manage`, `stock.read`, `trade.read/write`, `pos.operate/manage`, `analytics.read`,
  `sync.read/manage`, `payroll.read`. Матрица — `apps/api/src/modules/accounting/access/roles.ts`.
- **Нельзя выдать роль шире своей** (`canGrant`: все права роли должны быть у назначающего): администратор не
  создаёт, не правит, не понижает и не отключает владельца; собственную роль не поменять. То же в «Участниках».
- Пользователь создаётся вместе с членством; отмеченные в форме старые роли переводятся в роль организации.
  Глобальные роли больше не создаются. «Участники» ищут пользователя только у своего клиента (раньше — 500).
- `sql/pre/030`: старым пользователям без членства — членство из старых ролей (admin → admin, **не** владелец);
  без ролей — не создаётся (доступ выдаёт администратор).

## 8c. Поля зарплаты — только с `payroll.read`

Было: ведомость, суммы к выплате, оклад и IBAN — по `hr.read` (кадровик, руководитель); расчёт возвращал все суммы
кадровику; журнал аудита показывал оклад при приёме аудитору.

- Ведомость, выплаты, расчёт — `payroll.read`. Кадровик оформляет приём и изменения с окладом (кадровый приказ),
  но сумм не видит. В списках сотрудников (бухгалтерия и старый модуль), начислениях и кадровых записях журнала
  поля оплаты без `payroll.read` — `null` (`common/pay-fields.ts`).
- Попутно: IBAN был уникален на всю базу (один счёт нельзя указать в двух организациях; совпадение выдавало чужой
  счёт) — теперь в пределах договора. Приём — только в подразделение своей организации.

## 8d. MFA (TOTP)

- RFC 6238 без внешних библиотек (проверено на эталонных векторах RFC). Секрет — AES-256-GCM с `MFA_SECRET_KEY`
  (обязателен в production; `install.sh` генерирует), 8 одноразовых кодов восстановления — хэшами.
- При включённой MFA пароль даёт только 5-минутный токен-вызов (не access-токен); сессия — после кода.
  Код принимается один раз; 5 неверных подряд — блокировка второго фактора на 15 минут.
- **Привилегированные операции** требуют сессию, подтверждённую MFA (вход с кодом, `step-up` или провайдер с MFA):
  пользователи и роли, участники, подключения и запуск обмена 1С, учётная политика и настройки ЭСФ, закрытие и
  переоткрытие периода. В production — всегда (выключить: `MFA_ENFORCE=0`), вне его — при `MFA_ENFORCE=1`.

## 8e. Вход через OIDC

- Authorization Code + PKCE (S256); discovery и JWKS провайдера; `state`/`nonce`/verifier — одноразово на сервере
  (10 минут). `id_token`: подпись (только асимметричные алгоритмы — `none` и HS* отвергаются), `iss`, `aud`/`azp`,
  `exp`/`iat`, `nonce`.
- **Привязка только явная**: вошедший пользователь привязывает учётную запись провайдера; связь по
  `(issuer, subject)`. Email провайдера ничего не связывает (иначе — захват учётной записи). Одна учётная запись
  провайдера — один пользователь.
- `amr` с вторым фактором (otp, hwk, mfa…) — сессия подтверждена MFA. Refresh-токен — в cookie, браузер уходит в
  веб без токенов в адресе; ошибка — `?oidc_error=КОД`.
