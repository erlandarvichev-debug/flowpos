# FP-025: Товары, варианты, единицы, штрихкоды

**Status:** ⚠️ DONE_LOCAL — штрихкоды в пределах клиента, упаковки, весовые, варианты, версии товара, внешние сопоставления; экраны проверены визуально (локально, headless Chrome); не выкладывалось
**Date:** 2026-10-31
**Backlog:** Catalog · P1 · deps FP-009 · acceptance: *Stable item ID; дубли и weight barcode; versions и external mappings*

## Было

- **Штрихкод уникален во всей БД** (`product_barcodes.barcode @unique`): если у одного клиента есть Coca-Cola
  `5449000000996`, другой клиент этот товар со штрихкодом завести не мог (а ошибка уникальности выдавала, что код
  у кого-то есть).
- **Штрихкоды из МойСклад не находились на кассе:** воркер сохранял только первый код и только в поле
  `products.barcode`, а касса ищет в `product_barcodes`. То же — штрихкод из 1С.
- Весовых штрихкодов, штрихкодов упаковок, проверки контрольной цифры не было.
- Варианты (`parentId`) без правил: вложенность, одинаковые характеристики, штрихкод у родителя — всё допускалось.
- Истории изменений товара и реестра внешних идентификаторов не было.
- API каталога принимал **любые поля** из тела: можно было переписать `msId`/`onecGuid` (связь с учётной системой),
  `syncStatus`, `deleted`, `owner`.
- **Экраны каталога не работали с API:** форма слала `unitId`/`itemType` (в API — `uomId`/`kind`), создание товара
  падало; в карточке пустые «Единица» и «Тип»; НДС по умолчанию 12% (НК РК 2026 — 16%).

## Стало

- **Штрихкоды** (`catalog/barcode.ts`, чистые функции): нормализация (пробелы сканера), тип по содержимому
  (EAN-13/EAN-8/UPC-A/GTIN-14 с верной контрольной цифрой, иначе Code 128), строгая проверка явно указанного типа
  GS1 (опечатка не становится «внутренним кодом» молча). Уникальность — `@@unique([tenantId, barcode])`.
  Занятый код — 409 `BARCODE_TAKEN` с именем товара; если код у личного товара другой организации клиента — без
  имени и id.
- **Упаковки:** штрихкод с коэффициентом (`factor`, коробка = 12) и единицей упаковки. На кассе: количество в
  базовых единицах (qty × коэффициент), сумма — как оплачено, цена — за базовую единицу.
- **Весовые штрихкоды:** настройки клиента (`catalog_settings`: префиксы 20–29, длина PLU 4–6), PLU товара
  уникален у клиента. EAN-13 = префикс + PLU + граммы + контрольная. На кассе количество = вес из этикетки (цена за
  кг); неверная контрольная/чужой префикс/неизвестный PLU — товар не найден. Длину PLU нельзя сменить, пока есть
  товары с PLU другой длины.
- **Поиск по коду** (`resolveBarcode`): только товары, видимые организации (общий справочник + свой), не архивные;
  сначала точный код, затем весовой. `GET catalog/items/barcode/:code`; поиск в списке — и по штрихкоду/PLU/артикулу.
- **Варианты:** основной товар — товар клиента, не архивный, не вариант (без вложенности); характеристики
  обязательны; одна комбинация на основной товар (`variantKey` в каноническом виде, ключи без учёта регистра и
  пробелов; уникальность в БД). Штрихкоды — у вариантов: у основного с вариантами код не добавляется, а продажа по
  коду основного (пришедшему из обмена) — `VARIANT_REQUIRED`. Отвязка варианта возвращает вид «Товар».
- **Стабильный id и внешние сопоставления:** `external_mappings` (МойСклад/1С → id FlowPOS). Заполняет триггер БД
  на `products` (кто бы ни писал: API, воркеры, сиды). Пересоздание товара в МойСклад меняет внешний id — внутренний
  остаётся, прежняя связь — `DETACHED` с датой. Внешние id, статус обмена, архив через API не меняются (белый список
  полей).
- **Версии товара:** `product_versions` — снимок значимых полей и список изменённых, кто изменил (`updatedBy`),
  код трассировки; заполняет триггер (в т.ч. изменения из обмена). Служебные изменения (статус обмена, даты) и
  повтор тех же значений версию не создают. Версии неизменяемы (триггер).
- **Старое поле `products.barcode`** (его пишут обмен с 1С/МойСклад и старый код) зеркалится триггером в
  `product_barcodes` (`source = LEGACY`); код другого товара не перехватывается. **Отчёт «Дубли штрихкодов»** —
  товары, чей код из обмена уже у другого товара (поэтому на кассе не находится).
- **Воркер МойСклад** пишет все штрихкоды товара (`source = MOYSKLAD`, тип по ключу МойСклад), удаляет убранные,
  чужой код не перехватывает (предупреждение в лог).
- **Экраны:** список (поиск по штрихкоду, метки «вариантов: N», «вариант», «весовой PLU»; «Весовые штрихкоды»,
  «Дубли штрихкодов»); форма в полях API (вид, артикул, НДС 16% по умолчанию, PLU, штрихкод); карточка — штрихкоды с
  упаковкой и источником (добавить/убрать), варианты, история изменений, связи с учётными системами.
- **FP-024, доработка по визуальной проверке:** в карточке конфликта карантина — таблица «Что отличается» по ключевым
  реквизитам (сумма, даты, продавец…), а не только два сырых XML; причина в списке переносится, а не обрезается;
  в оповещениях «Кто действует» вместо повтора «Ответственный: Ответственный…».
- **Выкладка без `--accept-data-loss`:** столбцы `plu`/`variant_key` и уникальные индексы заранее создаёт
  `sql/pre/060_fp025_catalog_uniques.sql`; триггеры и перенос существующих данных (версия 1 каждому товару,
  сопоставления из `ms_id`/`onec_guid`, штрихкоды из старого поля) — `sql/070_fp025_catalog.sql`, идемпотентно.

## Проверка

- Юнит: `barcode.spec.ts` (5 — контрольные цифры по известным кодам, тип, строгий ввод, весовой разбор, настройки),
  `items.service.spec.ts` (обновлён: белый список полей, штрихкоды при создании), воркер МойСклад (все коды, тип,
  чужой код не перехватывается).
- Интеграционные `catalog.int-spec.ts` (6, настоящая БД): один EAN у двух клиентов; занятый код с именем / без
  имени для чужой организации; касса — штучный, упаковка (24 шт, 2200), весовой (1,234 кг × 2000 = 2468); PLU и
  настройки; старое поле → таблица, замена, не перехватывает, отчёт дублей (в т.ч. код у товара другой организации —
  без имени); варианты (все правила, отвязка); версии (что/кто, служебные без версии, неизменяемость, чужой — 404);
  пересоздание в МойСклад (DETACHED/ACTIVE, id стабилен, внешние id из API не меняются).
- HTTP под рабочей ролью `catalog-http.int-spec.ts` (3): EAN у двух клиентов, поиск по коду — свой товар, 409 с
  текстом; версии/сопоставления чужого — 404, **прямой запрос рабочей ролью в контексте другого клиента версий и
  штрихкодов не видит (RLS)**; весовые — `catalog.manage` для настроек (аудитор — 403), код из этикетки → товар,
  настройки клиента свои.
- **Мутации — 19/19 пойманы** (контрольная цифра, вес без контрольной, поиск без области организации, имя чужого
  товара в ошибке и в дублях, продажа родителя с вариантами, упаковка без коэффициента, вес от кассы, поля обмена из
  тела, вложенные варианты, ключ варианта без нормализации, штрихкод родителю, смена длины PLU, право на настройки,
  версия на служебные изменения, прежняя связь не отцепляется, старое поле перехватывает чужой код, МойСклад — только
  первый код, версии без проверки области). Первый прогон: 2 мутации не компилировались, 1 выжила — дубли с кодом у
  товара другой организации не показывались вовсе; исправлено в коде (показываются без имени) и тестах.
- **Визуальная проверка** (локально: API под рабочей ролью на `flowpos_test`, веб Vite, headless Chrome, демо-данные
  в «ТОО «Демо ЭСФ»»): ЭСФ — плашки оповещений, вкладка «Карантин» (список, карточка, конфликт с «Что отличается»),
  «Настройки» → состояние обмена; каталог — список с поиском, весовые, дубли, форма, карточки (штрихкоды с упаковкой,

## Не сделано / ограничения

- **Узкий экран (телефон):** общий каркас приложения не сворачивает боковое меню — содержимое сжато в узкую полосу.
  Это оболочка (`AppLayout`), не FP-025; нужна отдельная задача.
- Касса (`zhandos38/rmk`) должна передавать штрихкод как есть: для весового кода количество берётся из этикетки,
  для упаковки — пересчитывается. Контракт с кассой не проверялся (касса в другом репозитории).
- Цена за базовую единицу упаковки округляется до тиына (сумма строки — точно как оплачено).
- Воркер 1С пишет один штрихкод в старое поле — в таблицу его переносит триггер; несколько кодов из 1С — нет.
- Слияние дублей товаров (перенос остатков, документов, связей) — не сделано: дубли штрихкодов показываются,
  решает человек.
- Тест `legacy-scope` (FP-007) ищет свой товар среди первых 500 по алфавиту — хрупок к накоплению данных в общей
  тестовой БД (упал после прогонов без уборки; тесты FP-025 теперь за собой убирают).
