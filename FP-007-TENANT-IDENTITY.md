# FP-007: Клиент (tenant) и организация — составная идентичность

**Status:** ✅ DONE_LOCAL — приёмка выполнена и проверена локально (БД, сессия, старые модули, обмен, сквозной HTTP-тест); не выкладывалось. Остаток — в «Не сделано», в основном FP-008 (права) и FP-009 (RLS, outbox)
**Date:** 2026-10-30
**Backlog:** Platform · P0 · deps FP-001 · acceptance: *Два клиента и две организации не видят/не связывают чужие объекты*

Ночная версия FP-007 (`0feaaad`) откачена 30.10 — см. `docs/erp/AUDIT_2026-10-29_OVERNIGHT_MIGRATIONS.md`. Это новая реализация.

## Решения

1. **Клиент над организацией.** Таблица `tenants`; у каждой организации ровно один клиент (`organizations.tenant_id`).
   Пользователь (`users.tenant_id`) и членство (`org_memberships`) — только в организациях своего клиента.
2. **Справочники — уровень клиента, хозяйственные объекты — уровень организации** (ТЗ, «Ссылка включает tenant_id и id;
   для хозяйственных объектов также organization_id»). Товары, группы, единицы, типы цен, контрагенты и их группы
   несут `tenant_id`; `organization_id IS NULL` у товара/контрагента теперь значит «общий справочник **этого клиента**»,
   а не «общий для всей базы».
3. **Граница держится в БД, а не только в коде.** Ссылки — составные FK `(tenant_id, x_id) → (tenant_id, id)` и
   `(organization_id, x_id) → (organization_id, id)`. Ошибка фильтра в сервисе не даст связать чужое.
4. **Ключи объявлены в Prisma-схеме.** Проверено: `prisma db push` молча удаляет FK и индексы, созданные SQL-ем
   (ночной подход через SQL-миграции на этой выкладке не работал бы вообще).
5. **Код не обязан передавать `tenant_id`.** Значение по умолчанию — `NULLIF(current_setting('flowpos.tenant_id', true), '')`
   (будущий контекст RLS, FP-009); если пусто — триггер `fp_fill_scope` берёт значение у родителя, которого код уже указал
   (организация, документ, товар, склад…). Последний шаг для `tenant_id` — единственный клиент в БД. Клиентов несколько и
   неоткуда взять — отказ `NOT NULL` (fail-closed). Явно переданное значение не меняется — его проверяет FK.
   Зачем: автооткат `deploy.sh` возвращает старый код на новую схему; проверено, что клиент Prisma до FP-007 пишет в
   новую схему без ошибок.
6. **Миграция существующих данных — шаг до `db push`** (`prisma/sql/pre/010_fp007_tenant_identity.sql`, идемпотентно):
   клиент «Основной клиент» (`00000000-0000-0000-0000-000000000001`), заполнение `tenant_id`/`organization_id` от
   родителя, заранее созданные ключи `(scope, id)` (иначе `db push` требует `--accept-data-loss`), проверка уже
   существующих связей между организациями с понятной ошибкой. Подключено в `npm run push` и `deploy.sh`.

## Что закрыто составными FK

| Уровень | Связи |
|---|---|
| Клиент | организация ← пользователь, членство (+ пользователь), склад, касса, товар, контрагент, документ; товар → единица, группа, вариант; штрихкод, цена (+ тип цены), остаток (+ склад, ячейка), ячейка → склад, договор → контрагент, документ → контрагент, склады; строка документа → документ, товар; группы → родитель |
| Организация | касса → склад; подразделение → родитель; штатная единица → разряд; трудовой договор → физлицо; ставка разряда (новый `organization_id`) → разряд, вид ставки; кадровая история (новый `organization_id`) → договор, вид ставки; результат расчёта ЗП (новый `organization_id`) → период, договор; проводка → запись движений |

## Фаза 2: сессия и ссылки в учёте

- **JWT** (`jwt.strategy.ts`): токен подтверждает только «кто». Клиент и организация пользователя берутся из БД на каждый
  запрос; подмена `tenantId`/`organizationId` в токене ни на что не влияет. Отключённый или удалённый пользователь
  получает 401 сразу, а не по истечении токена (раньше — до 7 дней). В токене и ответе логина `tenantId` есть как подсказка.
- **`OrgContext.tenantId`** — из членства (строка БД). Системные контексты (автопилот, фоновая работа ЭСФ) — из документа
  или организации.
- **Проводки** (`PostingService.writeEntry` — через него идут все движения): каждая аналитика принадлежит клиенту и
  организации записи. Контрагент/товар — свой или общий справочник этого клиента; договор — по контрагенту; склад,
  подразделение, банковский счёт, касса, проект, статья — только своей организации. Иначе `REF_FOREIGN`.
- **Торговые документы** (`validateRefs`): «общий» контрагент или товар другого клиента больше не принимается.
- **Новая организация** создаётся у клиента её создателя (`RefsService.createOrganization`); `create-admin.mjs` заводит
  нового клиента; сиды — клиента по умолчанию.
- Проверка: `apps/api/test/tenant-session.int-spec.ts` — 5 тестов (подмена в токене, отключённый пользователь,
  `OrgGuard` и организация другого клиента, проводки, торговые документы). Мутация: без проверки в `writeEntry`
  падают 2 теста.

## Фаза 3: старые модули и обмен

Область — `common/scope.ts`: клиент и организация из пользователя, которого JWT-проверка подтвердила по БД; `id`,
`tenantId`, `organizationId` из тела запроса не принимаются (чужая организация в теле — 403). Отказ составного FK — 400.

| Модуль | Было | Стало |
|---|---|---|
| Каталог (товары, контрагенты, группы, единицы) | всё по всей базе, тело запроса пишется целиком | справочник клиента: общий или личный организации |
| Склады, остатки | чтение/изменение по `id` | своей организации |
| Пользователи | **чтение, смена пароля и отключение пользователя другого клиента по `id`**; тело целиком | своей организации, белый список полей |
| Аналитика | сводки по всей базе | своей организации |
| Торговля (заказы, отгрузки, приёмка, перемещения, списания, инвентаризация, POS-продажа) | списки и документы по всей базе, тело целиком, штрихкод по всей базе | своей организации; шапка — белый список; ссылки проверяются (`REF_FOREIGN`); номер — по своим документам |
| Касса | смена/касса по `id`; **продажи смены = все чеки базы за всё время** | своей организации; продажи — свои чеки со склада кассы с открытия смены |
| HR старого модуля | сотрудники, графики, табели, начисления всех организаций; **один табель на месяц на всю базу** | `organization_id` + составные FK; табель — на организацию; должности при найме — свои |
| Обмен с 1С/МойСклад | **ключи синхронизации глобальные (одинаковые GUID из одного шаблона 1С перезаписали бы товар другого клиента)**; склад — в первой попавшейся организации; **список подключений 1С всех организаций с паролем** | ключи — в пределах клиента; воркеры и адаптер пишут только в клиента/организацию подключения; подключения — свои и без пароля; очередь — своя |

Миграция кадров (`sql/pre/020`, `021`): организация выводится из договора, проводок, пользователя, подразделения,
склада; должность/график/табель нескольких организаций делится на копии; неоднозначно — выкладка останавливается
со списком точных `UPDATE` (столбцы уже добавлены). Проверено на копии dev-базы: 4 «ничьих» сотрудника при 2
организациях → остановка; после назначения — общая должность разделилась на 2 копии, общий табель — на 2.

Проверка: `test/legacy-scope.int-spec.ts` — 16 тестов (второй клиент настоящий, удаляется в `afterAll`), мутации по
каждому шагу ловятся (2 падения на мутацию). Юнит-тесты каталога и кассы мокали несуществующие модели (18 «старых»
падений) — переписаны; все юнит-тесты репозитория 90/90.

## Фаза 4: приёмка через HTTP

`apps/api/test/tenant-e2e.int-spec.ts` — 7 тестов на настоящем `AppModule` (JWT, `OrgGuard`, контроллеры, пайпы), вход
по паролю через `/auth/login`, клиент T1 (A1, A2) и T2 (B1, B2):
справочник клиента и личный справочник; документ со ссылкой на товар другого клиента и склад другой организации
(`400 REF_FOREIGN`); пользователь другого клиента — 404 на чтение/смену пароля/отключение, пароль жертвы прежний;
кадры и подключения 1С (пароль не отдаётся, чужая синхронизация — 404); бухгалтерия — организация другого клиента
и организация без членства — 403, при членстве документы организаций не смешиваются; подписанный сервером токен с
подменённым клиентом/организацией не расширяет доступ; отключённый пользователь и запрос без токена — 401.
Мутация: если JWT-проверка снова доверяет клиенту/организации из токена — тест падает.

Приложение в тесте поднимается `NestFactory` из `@nestjs/core` API: в корне монорепы лежит Nest 11
(`@nestjs/testing`), а API работает на Nest 10 — их нельзя смешивать.

## Не сделано
- **`SET LOCAL flowpos.tenant_id`** в транзакции запроса и `tenant_id` на остальных таблицах — вместе с RLS (FP-009).
- **Outbox без клиента/организации**; видимость очереди вычисляется по подключению или документу. Записи без
  `connectionId` (их ставят торговые сервисы) `push-worker` не отправляет, а `sync-queue.processor` помечает `DONE`
  без отправки — старый функциональный пробел, не утечка.
- **Права на операции** (кто может создавать пользователей, назначать роли, подключать 1С) — FP-008: сейчас любой
  вошедший пользователь организации.
- После отката релиза старый код HR не создаст сотрудника без пользователя/подразделения в базе с несколькими
  организациями (`NOT NULL`, fail-closed); в базе с одной организацией — работает.
- Аналитика проводок и ссылки без FK (`acc_postings.*_id`, `esf_invoices.counterparty_id`, банковские выписки) —
  проверка в коде (`writeEntry`), не в БД; `SETTLEMENT_DOC` не проверяется.
- Счёт проводки, личный справочник одной организации у другой организации того же клиента — проверка только в коде.
- Глобальная уникальность, мешающая клиентам: `product_barcodes.barcode`, `pos_terminals.code`, `users.email`
  (последний — осознанно: email — логин).
- `OpenShift`/`ShiftResponse`, `GigWorker`/`Marketplace*`, витрины `Mart*` в API не используются; часть получила
  организацию (смены), витрины и gig — нет.
