# FP-007: Клиент (tenant) и организация — составная идентичность

**Status:** ⚠️ IN PROGRESS — фаза 1 из 4 (уровень БД) готова и проверена; сессия, сервисы и сквозные тесты API — нет
**Date:** 2026-10-30
**Backlog:** Platform · P0 · deps FP-001 · acceptance: *Два клиента и две организации не видят/не связывают чужие объекты*

Ночная версия FP-007 (`0feaaad`) откачена 30.10 — см. `docs/erp/AUDIT_2026-10-29_OVERNIGHT_MIGRATIONS.md`. Это новая реализация.

## Решения

1. **Клиент над организацией.** Таблица `tenants`; у каждой организации ровно один клиент (`organizations.tenant_id`).
   Пользователь (`users.tenant_id`) и членство (`org_memberships`) — только в организациях своего клиента.
2. **Справочники — уровень клиента, хозяйственные объекты — уровень организации** (ТЗ, «Ссылка включает tenant_id и id;
   для хозяйственных объектов также organization_id»). Товары, группы, единицы, типы цен, контрагенты и их группы
   несут `tenant_id`; `organization_id IS NULL` у товара/контрагента теперь значит «общий справочник **этого клиента**»,
   а не «общий для всей базы».
3. **Граница держится в БД, а не только в коде.** Ссылки — составные FK `(tenant_id, x_id) → (tenant_id, id)` и
   `(organization_id, x_id) → (organization_id, id)`. Ошибка фильтра в сервисе не даст связать чужое.
4. **Ключи объявлены в Prisma-схеме.** Проверено: `prisma db push` молча удаляет FK и индексы, созданные SQL-ем
   (ночной подход через SQL-миграции на этой выкладке не работал бы вообще).
5. **Код не обязан передавать `tenant_id`.** Значение по умолчанию — `NULLIF(current_setting('flowpos.tenant_id', true), '')`
   (будущий контекст RLS, FP-009); если пусто — триггер `fp_fill_scope` берёт значение у родителя, которого код уже указал
   (организация, документ, товар, склад…). Последний шаг для `tenant_id` — единственный клиент в БД. Клиентов несколько и
   неоткуда взять — отказ `NOT NULL` (fail-closed). Явно переданное значение не меняется — его проверяет FK.
   Зачем: автооткат `deploy.sh` возвращает старый код на новую схему; проверено, что клиент Prisma до FP-007 пишет в
   новую схему без ошибок.
6. **Миграция существующих данных — шаг до `db push`** (`prisma/sql/pre/010_fp007_tenant_identity.sql`, идемпотентно):
   клиент «Основной клиент» (`00000000-0000-0000-0000-000000000001`), заполнение `tenant_id`/`organization_id` от
   родителя, заранее созданные ключи `(scope, id)` (иначе `db push` требует `--accept-data-loss`), проверка уже
   существующих связей между организациями с понятной ошибкой. Подключено в `npm run push` и `deploy.sh`.

## Что закрыто составными FK

| Уровень | Связи |
|---|---|
| Клиент | организация ← пользователь, членство (+ пользователь), склад, касса, товар, контрагент, документ; товар → единица, группа, вариант; штрихкод, цена (+ тип цены), остаток (+ склад, ячейка), ячейка → склад, договор → контрагент, документ → контрагент, склады; строка документа → документ, товар; группы → родитель |
| Организация | касса → склад; подразделение → родитель; штатная единица → разряд; трудовой договор → физлицо; ставка разряда (новый `organization_id`) → разряд, вид ставки; кадровая история (новый `organization_id`) → договор, вид ставки; результат расчёта ЗП (новый `organization_id`) → период, договор; проводка → запись движений |

## Проверка

- `apps/api/test/tenant-identity.int-spec.ts` — 7 тестов на реальной PostgreSQL: два клиента (второй — внутри
  откатываемой транзакции), организации A, A2 и B. Отказы БД при создании и изменении, вывод клиента из родителя,
  `SET LOCAL`, отказ без клиента при двух клиентах, новая организация у клиента создателя.
  Мутационная проверка: после удаления FK `acc_postings → acc_entries` тест падает.
- Миграция на копии dev-базы (2 организации, общие товары): строки до/после совпадают, у всех строк клиент,
  38 составных FK, повторный `npm run push` — без изменений. Пустая БД — тоже.
- Все тесты: интеграционные 53 + 1 skip, ЭСФ 230/230, юнит — те же 18 старых падений; сборка как в `deploy.sh` — exit 0.

## Не сделано (фазы 2–4)

- **Сессия:** `tenantId` в JWT и `OrgContext`; `SET LOCAL flowpos.tenant_id` в транзакции.
- **Чтение:** каталог (`catalog/*`), торговля, HR, касса, аналитика, пользователи фильтруют по клиенту/организации.
  Сейчас `hr.service` отдаёт сотрудников, графики и табели **всех** организаций; `payroll.service` берёт должность
  по имени из общей таблицы. Бухгалтерские `checkRefs`/`validateRefs` принимают «общий» товар/контрагента без
  проверки клиента.
- **Без организации вовсе:** `Employee`, `Position`, `WorkSchedule`, `TimeEvent`, `ShiftPlan`, `TimeSheet`, `Payroll` и др.
- **Аналитика проводок и ссылки без FK** (`acc_postings.counterparty_id/product_id/…`, `esf_invoices.counterparty_id`,
  банковские выписки) — пока только проверка в коде.
- Счёт проводки, личный справочник одной организации у другой организации того же клиента — проверка только в коде
  (общие счета плана и общий справочник клиента не укладываются в составной FK).
- Глобальная уникальность, мешающая клиентам: `product_barcodes.barcode`, `pos_terminals.code`.
- `tenant_id` на всех остальных таблицах — вместе с RLS (FP-009).
- Сквозной приёмочный тест через API: два клиента × две организации.
