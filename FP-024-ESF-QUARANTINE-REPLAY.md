# FP-024: Карантин входящих ЭСФ и контролируемая повторная обработка

**Status:** ⚠️ DONE_LOCAL — таксономия ошибок, карантин с исходным телом, конфликт «тот же ЭСФ — другое содержимое», повторная обработка и решения с причиной и журналом; экран визуально не проверен; не выкладывалось
**Date:** 2026-10-30
**Backlog:** ESF · P1 · deps FP-012, FP-017 · acceptance: *Error taxonomy; причина исправления; audit replay; same key different hash не заметается*

## Было

- Неразобранный входящий — запись в журнале (временный карантин FP-022, тело до 1 МБ); повторить обработку нельзя.
- **Битый XML, который парсер «съедает»** (`<a><b></a>`), и документ любого корня проходили как ЭСФ: в реестр
  попадала пустышка с номером = ID и **сегодняшней датой**. Пропущенный `invoiceType` молча становился
  `ORDINARY_INVOICE`, дата `31.02` — 3 марта, нечисловая сумма роняла запись.
- **Тот же ЭСФ с другим содержимым заметался:** `upsert` обновлял статус и молча игнорировал новое тело — расхождение
  с ИС ЭСФ никто бы не увидел.
- Уникальность «номер + дата» входящих была **по организации**, а не по продавцу: два поставщика с «№1 от 01.10» —
  ошибка уникальности, синхронизация падала **на каждом проходе** (курсор не двигался — входящие вставали навсегда).

## Стало

- **Проверка до записи** (`esf-inbound.ts`, чистая): XML корректен (валидатор, а не только парсер), корень `invoice`,
  версия конверта `InvoiceV2`, известный вид ЭСФ, обязательные реквизиты (номер, календарные даты дд.мм.гггг, ИИН/БИН
  продавца из 12 цифр, валюта, суммы — числа, ссылка на исходный для исправленного/дополнительного). Проблемы
  реквизитов — все сразу одним списком. Ничего не подставляется по умолчанию.
- **Таксономия** `INBOUND_ERRORS`: `ESF_IN_EMPTY_BODY`, `_XML_MALFORMED`, `_SCHEMA_UNKNOWN`, `_TYPE_UNSUPPORTED`,
  `_FIELD_INVALID`, `_HASH_CONFLICT`, `_KEY_CONFLICT`, `_LEGACY` — у каждой текст для бухгалтера, «что делать» и
  поможет ли повторная обработка. Временные сбои (сеть, БД) — не карантин: синхронизация падает, курсор стоит.
- **Карантин** — таблица `esf_inbound_quarantine` (RLS по организации, FP-009): тело **целиком** как получено,
  SHA-256, размер, конверт `invoiceInfo` без подписи/сертификата, код и деталь причины (маскированы), код
  трассировки. Одна запись на (ЭСФ, содержимое): повтор того же получения — «получен N раз», закрытая запись не
  открывается заново; другое содержимое — новая запись. Журнал `ESF_QUARANTINE_ADDED`. Курсор идёт дальше,
  карантинные не подтверждаются в ИС ЭСФ как полученные.
- **Тот же ЭСФ, другое содержимое** (`ESF_IN_HASH_CONFLICT`): реестр **не перезаписывается**; статус ИС ЭСФ из
  конверта применяется (он про документ с этим ID); запись в карантин с хэшем записи реестра; оповещение
  `ESF_QUARANTINE` становится **CRITICAL**. Разрешает человек:
  - «Принять новую версию» — только если новое тело проходит проверку, по документу нет исполненного решения,
    привязки основания, строк регистра НДС к зачёту и незавершённых решений, и запись реестра не менялась с момента
    обнаружения (два барьера: проверка и условный `updateMany` по хэшу в транзакции). Прежнее тело сохраняется в
    карантине (`replaced_body`), журнал `ESF_QUARANTINE_ACCEPTED_NEW` с хэшами и суммами до/после.
  - «Оставить полученную ранее» — реестр не меняется.
- **Номер + дата — в пределах продавца** (`@@unique([…, sellerTin, num, date])`); совпадение у **одного** продавца с
  другим ID — `ESF_IN_KEY_CONFLICT` в карантин, синхронизация не встаёт. Гонка двух проходов за один ЭСФ — повторное
  сравнение, а не карантин.
- **Повторная обработка** (`POST esf/quarantine/:id/replay`, `acc.esf.send`, причина ≥ 10 символов — «что
  исправлено»): сохранённое тело проверяется текущими правилами; ИС ЭСФ не вызывается; тело сверяется с хэшем
  (обрезанное при переносе — отказ). Успех — в реестр, запись `REPLAYED` со ссылкой на ЭСФ; уже в реестре — закрытие
  без дубля; неудача — запись открыта, попытка +1, причина обновлена. Закрытие — только из `OPEN` (опоздавший
  процесс не перезаписывает решение). Журнал `ESF_QUARANTINE_REPLAYED` / `_REPLAY_FAILED` с причиной и кодами.
  Конфликт содержимого и пустое тело повтором не обрабатываются. Подтверждение получения уходит на следующей
  синхронизации (досылаются все полученные и не подтверждённые).
- **Решения** (`POST esf/quarantine/:id/resolve`): `ACCEPT_NEW` | `KEEP_EXISTING` (только конфликты) | `DISMISS`,
  причина обязательна, журнал `ESF_QUARANTINE_RESOLVED`.
- **Перенос** `sql/060_fp024_quarantine_backfill.sql`: записи журнала `ESF_INBOUND_UNPARSED` → карантин с кодом
  `ESF_IN_LEGACY` (идемпотентно; уже попавшие в реестр пропускаются).
- **Экран:** вкладка «Карантин» (счётчик на вкладке): список с причиной и состоянием; карточка — что делать, тело
  (для конфликта — обе версии рядом), история, кнопки по правам. Метрика `flowpos_esf_quarantine_conflicts`.
- **Выкладка без `--accept-data-loss`:** новый уникальный индекс заранее создаёт
  `sql/pre/050_fp024_inbound_seller_unique.sql` (строго слабее прежнего — данные ему не противоречат).

## Не сделано / ограничения

- **Визуальная проверка вкладки «Карантин»** не проводилась (Windows-браузеры без доступа к localhost). Типы и
  сборка веба — зелёные; данные — через тот же API, что покрыт тестами.
- Повторная обработка использует сохранённое тело; повторно скачать документ из ИС ЭСФ по ID (например, для
  обрезанного тела из журнала FP-022) — нет.
- Статус ИС ЭСФ из конверта применяется и при конфликте содержимого (решение: статус относится к ID документа). Если
  ИС ЭСФ пересериализует тело при смене статуса, каждая смена даст запись конфликта (видимую, без потери данных) —
  проверить на реальном стенде в FP-023.
- Схема-уровень проверки — ключевые реквизиты, а не полная XSD входящего (полный реестр схем — FP-013).
- Цепочка исправлений (`correction_of`) и «новая версия как неизменяемая отдельная запись» из ТЗ — не здесь:
  принятая новая версия заменяет тело записи реестра, прежнее хранится в карантине.
