# Архитектура

## Решение по стеку
ТЗ предлагает Django + React для **нового** проекта. Бухгалтерия строится внутри существующего FlowPOS (решение владельца 18.10.2026: «всё в одном»), поэтому сохранён стек FlowPOS:
- backend: **NestJS (TypeScript)**, Prisma 5 + **PostgreSQL 16**;
- frontend: **Vue 3 + TypeScript + Element Plus**;
- фоновые задачи: **BullMQ/Redis** (уже используются воркерами sync/moysklad/push/analytics);
- API: REST, Swagger на `/api/docs`.

Причины: общая БД и модель данных с торговлей/кассой (автопилот проводок без интеграционного слоя), одна команда и один деплой, переиспользование авторизации, воркеров 1С/МойСклад. Деньги — `Decimal` (decimal.js в Prisma), в БД `NUMERIC(18,2)`.

## Модульный монолит
```
apps/api/src/modules/
  accounting/          ← бухгалтерский домен (этап 1)
    access/            роли, права, контекст организации (OrgGuard)
    chart/             план счетов + загрузка типового плана
    core/              PostingService (двойная запись) + rules/ (правила формирования проводок)
    documents/         жизненный цикл документов, версии, сторно
    periods/           закрытие и блокировка периодов
    reports/           ОСВ, карточка счёта, журнал
    refs/              справочники учёта, учётная политика, организации и участники
    common/            деньги/округление, понятные ошибки, идемпотентность
  catalog, trade, pos  ← торговый контур FlowPOS (источники автопилота, этап 2)
  hrms (этап 4)        ← кадры и зарплата РК (таблицы уже созданы)
  sync                 ← 1С/МойСклад
```
Домены ТЗ: организации/доступ (`access`, `refs`), справочники (`refs`, `catalog`), документы (`documents`), бухгалтерское ядро (`core`, `chart`, `periods`), склад/деньги (этап 2), зарплата/налоги (этап 4), отчётность (`reports`), интеграции (`sync` + этап 5), аудит (`audit_log`).

## Поток проведения
```
Документ (DRAFT) ──post──▶ транзакция:
   SELECT … FOR UPDATE документа
   advisory-lock (shared) периода организации → проверка закрытого периода
   правило(docType, version).build(doc) → проводки
   PostingService.validate: счета, группы, аналитики, кол-во, валюта, Дт=Кт
   прежняя ACTIVE-запись → SUPERSEDED (история), новая запись ACTIVE
   COMMIT → deferred-триггер БД ещё раз проверяет Дт=Кт по каждой записи
```
Автопилот (этап 2): торговые документы FlowPOS и кассовые смены становятся источниками (`sourceType = TRADE_DOCUMENT | POS_SHIFT`) того же `PostingService`.

## Изоляция клиентов
- каждый запрос бухгалтерии проходит `OrgGuard`: организация из `X-Organization-Id` (по умолчанию — организация пользователя), проверка членства и права;
- все бухгалтерские таблицы содержат `organization_id`, все запросы фильтруют по нему; ссылки аналитик на собственные справочники проверяются на принадлежность организации;
- ⚠️ торговые справочники FlowPOS (контрагенты, номенклатура) пока не имеют `organization_id` — общие на инсталляцию. Мульти-организационность торговых данных — задача этапа 2.

## Облако и сервер клиента
Один и тот же монолит: облако — несколько организаций/клиентов в одной БД с изоляцией по `organization_id`; on-premise — та же сборка на сервере клиента (Node 20+, PostgreSQL 16, Redis, nginx).
