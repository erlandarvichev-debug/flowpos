# ЭСФ: отправка и получение (ИС ЭСФ КГД МФ РК)

Раздел FlowPOS «Бухгалтерия → ЭСФ» (`/accounting/esf`). Код: `apps/api/src/modules/accounting/esf/`,
UI: `apps/web/src/views/accounting/EsfView.vue`, подпись: `apps/web/src/utils/ncalayer.ts`.

## Что делает

**Отправка (исходящие).**
1. ЭСФ формируется только из «Реализации» (DEMAND), которая проведена **и** отражена в бухгалтерии,
   то есть у неё есть действующая запись журнала проводок. Черновики и документы с проблемами автопилота не попадают в ЭСФ.
2. Суммы и НДС считаются той же функцией `tradeLineAmounts`, что и проводки, поэтому ЭСФ совпадает с учётом до тиына (это проверяется тестом).
3. Если включено «Готовить автоматически», фоновая задача (раз в минуту) сама формирует ЭСФ по новым реализациям.
   Если данных не хватает, документ остаётся в списке «Реализации без ЭСФ», а по кнопке «Сформировать» показывается список того, что нужно заполнить.
4. Отправка идёт так:
   - «Войти в ИС ЭСФ»: тикет `AuthService.createAuthTicket` подписывается в NCALayer ключом AUTH (XMLDSig), затем вызывается `SessionService.createSessionSigned`;
   - «Подписать и отправить»: FlowPOS пересобирает ЭСФ с датой выписки «сегодня» (графа A 2: дата выписки = день отправки);
   - NCALayer ставит «сырую» подпись ключом подписи на каждое тело ЭСФ;
   - вызывается `UploadInvoiceService.syncInvoice`.
5. Ответ ИС ЭСФ:
   - принятые ЭСФ получают статус SENT и id ИС ЭСФ;
   - отклонённые ФЛК получают статус REJECTED и текст ошибки с полем.
   «Обновить» запрашивает статусы (`queryInvoiceSummaryById`), а для FAILED — ошибки тяжёлого ФЛК (`queryInvoiceErrorById`).
   Если ответа по номеру не было (сбой связи), выполняется сверка по дате и номеру (`queryInvoiceSummaryByKey`).
6. Если документ изменили или отменили после отправки, ЭСФ помечается «требует исправления».
   Неотправленный ЭСФ по отменённому документу отменяется сам.

**Возврат покупателя → дополнительный ЭСФ.**
- Возврат, оформленный «на основании» реализации (`attributes.baseId`), даёт дополнительный ЭСФ (ADDITIONAL_INVOICE). В `relatedInvoice` попадают дата, номер и регистрационный номер ЭСФ реализации; дата оборота равна дате возврата.
- Количество и суммы указываются разницей со знаком «минус», цена за единицу — без изменения. Суммы совпадают с проводками возврата (это проверяется тестом).
- Контроль: основной ЭСФ должен быть зарегистрирован (есть регистрационный номер), покупатель тот же, а итог после всех дополнительных ЭСФ не уходит в минус (п. 11 Пояснения).

**Отзыв и подтверждения (подпись списка).**
- «Отозвать» доступно для основного ЭСФ с регистрационным номером (`revokeInvoiceById`, причина обязательна). Если покупатель — плательщик НДС, ИС ЭСФ ждёт его подтверждения (WAITING_CUSTOMER_REVOKE_CONFIRMATION), опрос доводит статус до REVOKED.
- Входящие исправленные и дополнительные ЭСФ можно «Подтвердить» (`approveInvoiceById`) или «Отклонить» с причиной (`declineInvoiceById`). Отзыв поставщика подтверждается кнопкой «Подтвердить отзыв» (`revokeConfirmInvoiceById`).
- Подписывается не ЭСФ, а служебный XML, который ИС ЭСФ собирает сама и сверяет байт в байт. Формат восстановлен по байт-коду SDK: `InvoiceSignatureHelper.toXML` → `JAXBUtils.toXml(obj, null, fragment=true, formatted=false)`, корень `signedContent` без пространства имён:
  - отзыв и отклонение: `<signedContent><idsWithReasons><idWithReason><id>…</id><reason>…</reason></idWithReason></idsWithReasons></signedContent>`;
  - подтверждения: `<signedContent><ids><id>…</id></ids></signedContent>`;
  - экранируются только `&`, `<`, `>`, как в JAXB.

**Получение (входящие).**
- При «Обновить» и в фоне, пока сессия открыта, выполняется `InvoiceService.queryUpdates(INBOUND)` с курсором (`esf_settings.inbound_last_*`), без дублей.
- Новые входящие ЭСФ отмечаются в ИС ЭСФ как полученные (`confirmInvoiceById` → DELIVERED).
- Поставщик определяется по БИН. Поступление того же поставщика на ту же сумму в пределах ±10 дней привязывается автоматически, только если найдено ровно одно такое поступление.

**Безопасность.** Ключ и пароль ЭЦП остаются на компьютере пользователя (NCALayer). Сервер хранит только sessionId, тела ЭСФ, подписи и сертификаты (это публичные данные). Вход, отправка и изменение настроек записываются в аудит.
Права:
- `acc.esf.read` — просмотр;
- `acc.esf.send` — формирование, вход и отправка (владелец, администратор, главбух, бухгалтер);
- настройки — `acc.policy.manage`.

ИИ-агент через MCP (`esf_invoices`) только видит реестр. Подписывать и отправлять он не может.

## Что нужно заполнить перед первой выпиской
1. **Организация:** БИН (12 цифр), наименование, адрес.
2. **Настройки ЭСФ:**
   - ИИН владельца ЭЦП;
   - дата постановки на учёт по НДС (для плательщиков);
   - способ отправления (E 29);
   - признак происхождения товаров по умолчанию (G 2).
3. **Покупатели:** ИИН/БИН.
4. **Единицы измерения товаров:** коды классификатора ИС ЭСФ. У единиц из МойСклада код уже стоит.
5. **Отдельный признак происхождения или код ТН ВЭД:** в карточке товара, `attributes.esf.truOriginCode`, `tnvedCode`, `catalogTruId`, `gtinCode`. В UI карточки товара этих полей пока нет.
6. **NCALayer** на компьютере подписанта и регистрация организации в ИС ЭСФ (для тестового стенда — тестовые ключи НУЦ РК).

## Проверено
- Тесты `apps/api/test/accounting-esf.int-spec.ts` на БД `flowpos_test`, 10 штук (плюс возврат → дополнительный ЭСФ; отзыв с точной строкой подписи; подтверждение входящих):
  - XSD;
  - суммы против проводок;
  - неплательщик НДС;
  - нехватка данных;
  - только учтённые документы;
  - полный цикл «тикет → сессия → подпись → отправка → отказ ФЛК → DELIVERED → документ отменён, ЭСФ требует исправления»;
  - сброс закрытой сессии;
  - входящие: загрузка, привязка к поставщику и поступлению, отметка «получено», без дублей при повторе.
- Ответы ИС ЭСФ в этих тестах имитируются по WSDL.
- Живой вызов тестового стенда — `ESF_LIVE=1`. Выдачу тикета (`createAuthTicket`) стенд выполняет: проверено 23.10.2026.

## Не проверено и не реализовано (честно)
- **Отправка в реальную ИС ЭСФ не выполнялась.** Тестовые ключи из SDK КГД просрочены с 2019 года. Актуальные тестовые ключи НУЦ РК выдаются по заявке владельца ИС (pki.gov.kz → «Разработчикам → Первичное получение SDK»).
  Без них не подтверждены:
  - форма тела: выбран канонический вид SDK (без XML-декларации, только xmlns:v2) — подтвердить на стенде;
  - `catalogTruId = 1`;
  - ответы ФЛК на реальные данные.
- Исправленный ЭСФ (FIXED_INVOICE) из FlowPOS не выписывается: исправление делается отзывом и новым ЭСФ или в ИС ЭСФ. Дополнительный ЭСФ на изменение цены (без возврата) тоже не выписывается.
- Знак «минус» в количестве дополнительного ЭСФ и неизменная цена за единицу — распространённая практика. Подтвердить её должны ФЛК тестового стенда и главбух.
- СНТ, «Виртуальный склад», товары с признаками 1–2 (данные декларации), экспорт и валюта, совместная деятельность, госучреждения (раздел C1) — не реализовано.
- Сверка «НДС к зачёту только по полученным ЭСФ» (отчёт) — следующий шаг.
- Список кодов «способ отправления» в UI: коды 10–90 даны по памяти о классификаторе КТС № 378, прил. 3. **Нужно сверить с текстом решения.**
