# План: подписки на решения и решение «Супервайзер»

Дата: 16.11.2026. Автор плана — разработчик решения «Супервайзер». ERP ведёт второй разработчик.
Статус: **черновик на согласование**. Код не написан, на сервере ничего не менялось.

## 1. Что получится

- **Админка платформы** на flowpos.kz (видна только владельцу платформы): организации и какие
  решения у каждой подключены по подписке — статус, срок, число мест.
- **Решение «ERP»** — то, что уже работает. Его код не меняется; у существующих организаций
  подписка на ERP включается автоматически, чтобы у них ничего не пропало.
- **Решение «Супервайзер»** — рабочее место супервайзера на сайте и раздел «Маршрут» в агенте
  на телефоне:
  - супервайзер заводит торговых представителей, ставит им задания и маршруты на день;
  - представитель в агенте видит маршрут и задания, отмечает посещение, делает фото;
  - у каждого посещения и заказа отметка: **на точке** (телефон рядом с клиентом) или **удалённо**;
  - супервайзер видит посещения, фото, план/факт и точки на карте за день.

## 2. Как устроен проект сейчас (важное для плана)

- Доступ даёт членство пользователя в организации (`OrgMembership.role`) и матрица прав
  `ROLE_PERMISSIONS` (`apps/api/src/modules/accounting/access/roles.ts`). Роли сейчас: владелец,
  администратор, бухгалтеры, кадры, кассир, кладовщик, менеджер, аудитор.
- **Администратора платформы нет**: первую организацию создаёт скрипт `create-admin.mjs`.
- **Подписок, тарифов и отключения разделов по организациям нет** — единственное ограничение — права роли.
- Данные организаций разделены на уровне базы (RLS, FP-009): любая новая таблица обязана иметь
  `tenant_id` и `organization_id`, иначе выкладка остановится.
- Схема базы — `packages/db/prisma/schema.prisma`, применяется `prisma db push` без потери данных.
- **Загрузки файлов в API нет** (ни фото, ни вложений). nginx пропускает до 25 МБ.
- Вход рассчитан на браузер: обновление сессии — только через cookie. Для телефона нужен свой способ.
- Раздел «Акт сверки» в ERP есть (отчёт и печатная форма RECON) — он считает по данным ERP,
  а агент берёт расчёты из МойСклад; это разные источники.

## 3. Часть А. Подписки и админка платформы

**База** (новые таблицы, обе с `tenant_id`/`organization_id`):
- `org_subscriptions` — организация, решение (`erp` | `supervisor`), статус (`trial` | `active` |
  `suspended`), действует до, число мест (для «Супервайзера» — сколько представителей), примечание.
- `subscription_events` — журнал: кто, когда и что изменил в подписке.

**Сервер** (новый модуль `platform`, существующие модули не меняются):
- Администратор платформы — по списку адресов в настройке `PLATFORM_ADMIN_EMAILS` (в продакшене
  обязателен второй фактор). Отдельная проверка, не роль организации.
- `GET /platform/organizations`, `GET/PUT /platform/organizations/:id/subscriptions`.
- Проверка `@RequireSolution('supervisor')` на всех адресах «Супервайзера»: нет активной
  подписки или срок вышел — отказ с понятным текстом.
- `GET /subscriptions/mine` — сайт узнаёт, какие решения показывать в меню.
- Существующим организациям при выкладке создаётся активная подписка `erp` без срока.

**Сайт:** раздел «Платформа» (только администратору платформы): таблица организаций, карточка
организации с переключателями решений, сроком и числом мест. Пункты меню «Супервайзера» видны
только при активной подписке.

**Чего в этой части нет:** адреса ERP подпиской не закрываются (это код второго разработчика) —
при `suspended` ERP на первом шаге только скрывается в меню. Оплата онлайн и счета — не входят.

## 4. Часть Б. «Супервайзер» на сервере и сайте

**Роли** (добавляются в общий `roles.ts` — только новые строки):
- `supervisor` — управляет представителями, точками, маршрутами, заданиями, видит всё по своей организации;
- `sales_rep` — работает только через агента, на сайт не входит, видит только своё.

**База** (все таблицы `field_*`, с `tenant_id`/`organization_id`):

| Таблица | Что хранит |
|---|---|
| `field_reps` | представитель: имя, телефон, логин МойСклад, супервайзер, активен |
| `field_devices` | привязанные телефоны: модель, версия агента, последний выход на связь |
| `field_points` | торговые точки: название, адрес, телефон, id контрагента МойСклад, координаты, радиус |
| `field_routes`, `field_route_stops` | маршрут представителя на дату и его точки по порядку |
| `field_tasks` | задание: кому, по какой точке, срок, текст, статус, результат |
| `field_visits` | посещение: начало, конец, координаты, расстояние до точки, «на точке/удалённо», комментарий |
| `field_photos` | фото посещения: файл, время, координаты |
| `field_orders` | заказ из агента: номер в МойСклад, сумма, «на точке/удалённо», координаты |
| `field_track` | отметки местоположения по событиям |

**Точки (клиенты).** Клиенты представителя живут в МойСклад, координат там нет. Агент при
загрузке клиентов передаёт их список на сервер (название, адрес, телефон, id в МойСклад);
координаты точки сохраняются при первом посещении («Запомнить место») или супервайзер ставит
точку на карте.

**«На точке» или «удалённо».** Сервер сам сравнивает координаты телефона с координатами точки:
в пределах радиуса (по умолчанию 100 м, настраивается) — «на точке», иначе «удалённо»; у точки
нет координат или телефон не дал местоположение — «не определено». Решение принимает сервер,
а не телефон.

**Фото.** Телефон сжимает снимок (до ~300 КБ), сервер хранит в `/opt/flowpos/shared/data/field/…`
(вне каталога релиза — релизы стираются). На диске сервера свободно 8 ГБ: при 300 КБ это около
25 000 фото. Нужен срок хранения (предлагаю 180 дней) или больший диск.

**Сайт — раздел «Торговые»:**
- «Представители» — список, привязка телефона, кто на связи;
- «Точки» — список и карта, правка координат;
- «Маршруты» — маршрут представителя на день: выбрать точки, расставить порядок, копировать на другой день;
- «Задания» — поставить, увидеть выполнение;
- «Посещения» — лента с фото, отметкой «на точке/удалённо», длительностью;
- «День на карте» — точки плана, посещения и отметки местоположения представителя за день;
- «План/факт» — сколько точек запланировано, посещено, пропущено, сколько заказов и на какую сумму.

Карта — Leaflet с картой OpenStreetMap (бесплатно, без ключей).

## 5. Часть В. Агент на телефоне

- **Привязка.** Супервайзер нажимает «Привязать телефон» — сайт показывает код из 6 цифр
  (действует 15 минут). Представитель вводит код в агенте один раз. Пароль от сайта ему не нужен.
  Вход в МойСклад в агенте остаётся как есть — каталог и заказы по-прежнему идут в МойСклад.
- **Раздел «Маршрут»:** точки на сегодня по порядку, задания, кнопка «Начать посещение».
- **Посещение:** местоположение → фото (одно или несколько) → заказ (как сейчас) → комментарий →
  «Завершить». Задание закрывается с результатом.
- **Без связи:** посещения, фото и отметки копятся в телефоне и досылаются, как сейчас заказы.
- **Заказ:** в сам заказ МойСклад дописывается строка «Оформлен на точке» / «Оформлен удалённо».
- Нужны разрешения Android: местоположение и камера. Постоянного слежения в фоне на первом
  этапе нет — координаты берутся в момент посещения, фото и заказа.

## 6. Порядок работ

| Этап | Что | Где видно результат |
|---|---|---|
| 1 | Подписки, администратор платформы, раздел «Платформа» | сайт |
| 2 | Роли, представители, точки, задания, маршруты; адреса для агента | сайт |
| 3 | Агент: привязка, маршрут, задания, посещение с местоположением и фото, отметка в заказе | телефон |
| 4 | Посещения с фото, день на карте, план/факт | сайт |
| 5 | Печатная форма акта сверки в агенте (от сервера не зависит) | телефон |

Каждый этап — отдельная выкладка, каждая только по слову владельца: выкладка меняет базу рабочего
сервера. Перед выкладкой скрипт проекта делает резервную копию базы.

## 7. Что нужно решить до начала

1. **Общий репозиторий со вторым разработчиком.** Git на сервере нет, выкладка заменяет проект
   целиком: кто выложил последним, тот затёр другого. Без общего репозитория начинать нельзя.
2. **Общие файлы.** Мне придётся дописать строки в пять общих файлов: `app.module.ts`,
   `schema.prisma`, `roles.ts`, `router/index.ts`, `AppLayout.vue`. Второй разработчик должен об этом знать.
3. **Администратор платформы** — чьи адреса входят в список.
4. **Срок хранения фото** и радиус «на точке».
5. **Память сервера.** 1 ГБ, свободной почти нет; сборка релиза на таком сервере идёт на пределе.
   Фото и карта нагрузку на память почти не добавляют, но запас нужен.
