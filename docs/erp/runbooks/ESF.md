# Runbook: обмен с ИС ЭСФ

Для дежурного инженера и ответственного за ЭСФ. Каждое оповещение FlowPOS (`ops_alerts`, вебхук, журнал службы,
плашка на экране «ЭСФ») и каждое правило Prometheus ссылается на раздел этого файла.

**Важно.** Метрики и логи показывают техническое состояние обмена. Юридическое принятие документа подтверждает только
статус в ИС ЭСФ (карточка ЭСФ → «Реквизиты»). Никакое действие из этого runbook не «досылает» ЭСФ в обход сверки.

## Где смотреть

| Что | Где |
|---|---|
| Оповещения организации и состояние обмена | Бухгалтерия → ЭСФ (плашка сверху); «Настройки» → «Состояние обмена с ИС ЭСФ» |
| Метрики всех организаций | `curl -s -H "Authorization: Bearer $OPS_METRICS_TOKEN" http://127.0.0.1:3000/api/v1/ops/metrics` (на сервере) |
| Логи API (без секретов, с кодом трассировки) | `journalctl -u flowpos-api --since -1h \| grep -E 'ESF|ALERT'` |
| Вызовы ИС ЭСФ | строки `[ESF-GW]`: операция, среда, исход, длительность (ошибки — всегда; успешные — уровень debug, в бою только при `LOG_DEBUG=1`) |
| Все действия по запросу/проходу | `select ts, action, entity, entity_id from audit_log where trace_id = '<код>' order by ts;` |

**Код трассировки.** Каждое действие в интерфейсе получает код (`X-Request-Id`); пользователь видит его в сообщении
об ошибке («Код обращения: …»). Фоновый проход по организации — `esf-tick-<uuid>`. По коду находятся строки лога
(`[trace <код>]`), записи журнала (`audit_log.trace_id`) и оповещения (`ops_alerts.trace_id`).

## Ответственные

| Кто | Чем занимается |
|---|---|
| **Ответственный за ЭСФ в организации** (бухгалтер, право `acc.esf.send`) | вход в ИС ЭСФ ключом, сверка UNKNOWN, исправление отклонённых, ключи |
| **Ответственный за решения ЭСФ** (право `acc.esf.approve`) | решения по входящим (FP-018) |
| **Дежурный инженер FlowPOS** | процесс API, фоновая обработка, связь с ИС ЭСФ, БД, вебхук |

## Оповещения FlowPOS

<a id="esf-unknown"></a>
### ESF_UNKNOWN — результат отправки неизвестен
**Значит:** ответ ИС ЭСФ на отправку потерян (сеть, таймаут, сбой процесса). ЭСФ **мог быть принят**. Повторная
отправка заблокирована (FP-017). Предупреждение — старейшему больше 30 мин, критично — больше суток.
**Ответственный:** бухгалтер. **Действия:**
1. Убедиться, что есть вход в ИС ЭСФ (иначе см. [ESF_NO_SESSION](#esf-no-session)).
2. Вкладка «Требуют решения» → строка UNKNOWN → «Сверить статус». Сверка ищет ЭСФ по дате и номеру.
3. Найден — статус обновится сам, оповещение закроется на следующем проходе.
4. Не найден — сверка доказательна только через 10 минут после отправки. После неё в карточке появится
   «Разрешить повторную отправку» (с причиной; действие в журнале).
5. **Не создавать ЭСФ заново вручную** в портале ИС ЭСФ, пока UNKNOWN не разрешён, — получится дубль.

<a id="esf-sending-stuck"></a>
### ESF_SENDING_STUCK — отправка зависла
**Значит:** ЭСФ в состоянии «отправляется» дольше 5 минут, а фоновое восстановление (SENDING → UNKNOWN) не сработало.
Почти всегда фоновая обработка не идёт. **Ответственный:** дежурный инженер. **Действия:**
1. `systemctl status flowpos-api`; в логе — есть ли строки прохода (`[trace esf-tick-…]`).
2. Проверить `ESF_WORKER_DISABLED` в `api.env` (должно быть пусто/не 1) и метрику `flowpos_esf_worker_last_tick_age_seconds`.
3. Перезапуск API (`systemctl restart flowpos-api`) — восстановление переведёт такие ЭСФ в UNKNOWN; дальше — [ESF_UNKNOWN](#esf-unknown).
4. **Не переводить** статус в БД руками в READY: ЭСФ мог дойти до ИС ЭСФ.

<a id="esf-sync-failing"></a>
### ESF_SYNC_FAILING — синхронизация не удаётся подряд
**Значит:** проход «статусы + входящие» падает 3 раза подряд (критично — 10). Текст последней ошибки — в оповещении
и в «Состоянии обмена» (без секретов). **Ответственный:** дежурный инженер. **Действия по коду ошибки:**
- `ESF_NETWORK` — нет связи с `test3.esf.kgd.gov.kz`/`esf.gov.kz:8443`: DNS, исходящий файрвол, сертификат. Проверка с сервера: `curl -sS -o /dev/null -w '%{http_code}\n' https://esf.gov.kz:8443/esf-web/ws/api1/SessionService?wsdl`.
- `ESF_SESSION_CLOSED` — сессия истекла; FlowPOS закрыл её у себя → оповещение сменится на [ESF_NO_SESSION](#esf-no-session).
- `ESF_ACCESS_DENIED` / `ESF_SECURITY_ERROR` — права пользователя ИС ЭСФ или ключ AUTH; передать бухгалтеру.
- `ESF_BAD_RESPONSE` / `ESF_FAULT` — ответ ИС ЭСФ; сверить с новостями КГД о работах; собрать код трассировки и время.

<a id="esf-sync-stale"></a>
### ESF_SYNC_STALE — давно не было успешной синхронизации
**Значит:** вход в ИС ЭСФ есть, ошибок подряд нет, но успешного прохода не было 2 ч (критично — 24 ч). Похоже на
остановленную фоновую обработку. **Действия:** как в [FlowposEsfWorkerStalled](#flowpos-esf-worker-stalled).
Временно бухгалтер может нажать «Обновить статусы и входящие».

<a id="esf-no-session"></a>
### ESF_NO_SESSION — нет входа в ИС ЭСФ, а работа есть
**Значит:** есть ЭСФ на сверке или давно готовые к отправке, а сессии нет — статусы и входящие не обновляются.
**Ответственный:** бухгалтер. **Действия:** «Войти в ИС ЭСФ (ЭЦП)» — подписать тикет ключом AUTH в NCALayer.

<a id="esf-quarantine"></a>
### ESF_QUARANTINE — входящие не разобраны
**Значит:** ИС ЭСФ отдала входящий ЭСФ, который FlowPOS не смог разобрать. Раньше такой документ пропадал молча;
теперь тело как получено, SHA-256 и причина сохраняются в журнале (`action = 'ESF_INBOUND_UNPARSED'`, `entity_id` =
идентификатор ЭСФ в ИС ЭСФ). **Ответственный:** бухгалтер + поддержка FlowPOS. **Действия:**
1. Бухгалтер видит документ в портале ИС ЭСФ по регистрационному номеру из оповещения/журнала и при необходимости
   работает с ним там.
2. Поддержка: `select entity_id, after->>'registrationNumber', after->>'error', after->>'bodySha256' from audit_log where action = 'ESF_INBOUND_UNPARSED' and organization_id = '<org>';` — передать разработке пример (тело — в `after->>'body'`).
3. Повторная обработка из карантина — FP-024 (пока нет). Запись уходит из счётчика, как только ЭСФ с этим
   идентификатором появится в реестре.

<a id="esf-signing-failures"></a>
### ESF_SIGNING_FAILURES — отказы проверки подписи
**Значит:** за сутки ≥ 3 раза подпись не прошла проверку FlowPOS (не тот ключ, чужой сертификат, подписаны другие
байты, истёк запрос на подпись). **Ответственный:** бухгалтер. **Действия:** коды — в журнале
(`action = 'ESF_SIGNING_REJECTED'`, `after->>'code'`): `ESF_SIGNER_NOT_AUTHORIZED` — ключ не того ИИН/БИН или
не ключ подписи (RSA/GOST, не AUTH); `ESF_SIGNATURE_INVALID` — подписаны не те данные: подписать заново из FlowPOS;
`ESF_SIGN_REQUEST_INVALID` — запрос на подпись устарел: обновить страницу и подписать заново.

<a id="esf-rejected"></a>
### ESF_REJECTED — ИС ЭСФ отклонила ЭСФ
**Ответственный:** бухгалтер. **Действия:** вкладка «Ошибки» → фильтр по коду ошибки → исправить данные документа
(контрагент, БИН, адрес, классификаторы) → ЭСФ пересоберётся при следующей подписи.

<a id="esf-decisions-overdue"></a>
### ESF_DECISIONS_OVERDUE — просрочены решения
**Ответственный:** ответственный за решения. **Действия:** вкладка «Решения» → утвердить/отклонить. Сроки задаёт
методолог в правилах решений (настройки ЭСФ); FlowPOS юридические сроки не придумывает.

## Правила Prometheus (`deploy/monitoring/flowpos-esf.rules.yml`)

<a id="flowpos-api-down"></a>
### FlowposApiDown
`systemctl status flowpos-api`, `journalctl -u flowpos-api -n 200`. Частые причины: не задан секрет в `api.env`
(API пишет, какой), БД недоступна, порт занят. После подъёма проверить, нет ли [ESF_SENDING_STUCK](#esf-sending-stuck).

<a id="flowpos-esf-worker-stalled"></a>
### FlowposEsfWorkerStalled
Проход по организациям не завершался 10 минут. Проверить `ESF_WORKER_DISABLED`, зависание долгого вызова ИС ЭСФ
(строки `[ESF-GW]` без завершения; таймаут вызова 60 с), нагрузку на БД. Перезапуск API безопасен: незавершённые
отправки станут UNKNOWN и пройдут сверку.

<a id="outbox-lease-expired"></a>
### FlowposOutboxLeaseExpired
Сообщение очереди в 1С «отправляется», а аренда истекла — воркер `flowpos-worker@push` упал или завис.
`systemctl status 'flowpos-worker@push'`. Захват сообщения снова — после истечения аренды автоматически (FP-021);
сообщения в UNKNOWN разбирает оператор.

## Подавление повторов

Одно открытое оповещение на ключ и организацию (уникальность в БД). Повторное уведомление той же важности —
не чаще раза в 6 ч (WARNING) / 1 ч (CRITICAL); рост важности — сразу; закрытие — отдельным уведомлением
«RESOLVED». История — `ops_alerts` (закрытые остаются) и журнал (`OPS_ALERT_RAISED` / `OPS_ALERT_RESOLVED`).

## Чего в логах и уведомлениях нет

Подписи, сертификаты, тикеты входа, идентификаторы сессий ИС ЭСФ, токены, пароли (в т.ч. в адресах БД) маскируются
глобальным логгером и при записи ошибок/оповещений (`apps/api/src/common/redact.ts`). Если секрет всё же попал в
лог — это дефект: зафиксировать строку (без пересылки самого секрета), ротировать секрет, завести задачу.
