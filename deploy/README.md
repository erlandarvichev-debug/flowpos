# Установка FlowPOS на сервер

Комплект готов, но **ещё не разворачивался**. Установка — по решению владельца.

Схема: один сервер Ubuntu 22.04/24.04, без Docker, systemd + nginx + PostgreSQL 16 + Redis (как на остальных проектах VPNet).

```
https://app.<домен>  → nginx → веб (статика) + /api → FlowPOS API :3000 (127.0.0.1)
https://mcp.<домен>  → nginx → MCP для клиентов :3100 (127.0.0.1) — подключение Claude
/opt/flowpos/
  releases/<дата>/   — релизы (хранятся 5 последних)
  current → releases/<активный>
  shared/api.env, mcp.env (600) · shared/data/ (состояние MCP) · shared/backups/
```

## Что нужно от владельца
1. **Сервер.** Ubuntu 22.04/24.04, 2 vCPU / 4 ГБ RAM / 40 ГБ диска для начала, root по SSH.
2. **Два имени в DNS** на IP сервера: `app.<домен>` и `mcp.<домен>` (например, `app.flowpos.kz`, `mcp.flowpos.kz`).
3. **Решение по данным.** Новый сервер стартует с пустой базой и первым администратором. Переносить ли данные из локальной базы — решить отдельно.

## Установка (первый раз)
```bash
# на своём компьютере
bash deploy/scripts/make-release.sh                       # → flowpos-release-YYYYMMDD-HHMM.tar.gz (без секретов и node_modules)
scp flowpos-release-*.tar.gz root@SERVER:/tmp/
scp -r deploy root@SERVER:/root/flowpos-deploy

# на сервере
sudo APP_DOMAIN=app.flowpos.kz MCP_DOMAIN=mcp.flowpos.kz bash /root/flowpos-deploy/scripts/install.sh
#   ставит Node 22, PostgreSQL 16, Redis, nginx, certbot; создаёт пользователя flowpos, базу,
#   секреты (JWT_SECRET, пароль БД, MCP_STATE_KEY) в /opt/flowpos/shared/*.env, службы, бэкап в cron

certbot certonly --standalone -d app.flowpos.kz -d mcp.flowpos.kz \
  --pre-hook 'systemctl stop nginx' --post-hook 'systemctl start nginx'
ln -s /etc/nginx/sites-available/flowpos.conf /etc/nginx/sites-enabled/ && nginx -t && systemctl reload nginx

sudo bash /root/flowpos-deploy/scripts/deploy.sh /tmp/flowpos-release-*.tar.gz

# первый администратор и организация (пароль печатается один раз)
cd /opt/flowpos/current && sudo -u flowpos bash -c 'set -a; . /opt/flowpos/shared/api.env; set +a; \
  node deploy/scripts/create-admin.mjs --email owner@company.kz --org "ТОО Компания" --bin 123456789012 --first Имя --last Фамилия'
```
Демо-seed (`admin@flowpos.kz / admin123`) на бою **не запускать**.

## Тестовый стенд в локальной сети (без домена и TLS)
`sudo bash deploy/scripts/lan-stand.sh` — штатный `install.sh` плюс nginx по HTTP на адресе сервера, фоновая обработка ЭСФ
выключена, второй фактор не обязателен, mDNS (`http://<hostname>.local` — адрес из DHCP может меняться), firewall:
SSH/веб только из локальной сети. Затем `deploy.sh` и `create-admin.mjs`, как ниже. **Не для прода и не для доступа
из интернета** (HTTP без шифрования; для удалённого доступа — VPN до роутера, а не проброс портов).

## Обновление
```bash
bash deploy/scripts/make-release.sh && scp flowpos-release-*.tar.gz root@SERVER:/tmp/
ssh root@SERVER 'bash /root/flowpos-deploy/scripts/deploy.sh /tmp/flowpos-release-….tar.gz'
```
`deploy.sh` выполняет шаги по порядку:
1. Сборка.
2. Бэкап БД.
3. Подготовка данных (`prisma/sql/pre/*.sql`): новые столбцы и их заполнение для существующих данных. Если данные противоречат новым правилам (например, ссылка на объект другой организации), выкладка остановится с понятным сообщением.
4. Схема БД через `prisma db push` без `--accept-data-loss`. Изменение, при котором теряются данные, остановит выкладку до переключения.
5. SQL-инварианты и триггеры (`prisma/sql/*.sql`).
6. Переключение `current`.
7. Перезапуск служб.
8. `healthcheck.sh`.

Если проверка не прошла, код откатывается на прошлый релиз. Схема БД при этом назад не откатывается, бэкап `pre-deploy` лежит в `shared/backups`.

## Службы
| Служба | Что | Порт |
|---|---|---|
| `flowpos-api` | API + автопилот бухгалтерии (15 с) + фоновая работа ИС ЭСФ (60 с) | 127.0.0.1:3000 |
| `flowpos-mcp` | MCP для клиентов (OAuth) | 127.0.0.1:3100 |
| `flowpos-worker@moysklad-worker` и др. | обмен с МойСклад/1С, push, аналитика — **включать только используемые** | — |

Журналы: `journalctl -u flowpos-api -f`. Проверка: `bash deploy/scripts/healthcheck.sh`.

## Бэкап и восстановление
- Ежедневно в 03:30: `pg_dump -Fc` + состояние MCP, хранятся 14 дней. Перед каждой выкладкой делается отдельный бэкап, он хранится 30 дней. Каждый дамп сразу проверяется `pg_restore --list`.
- Восстановление — от владельца (роль миграций): `systemctl stop flowpos-api flowpos-mcp && pg_restore --clean --if-exists --no-owner -d "$MIGRATION_DATABASE_URL" <файл.dump> && (cd /opt/flowpos/current/packages/db && DATABASE_URL="$MIGRATION_DATABASE_URL" node scripts/apply-sql.js) && systemctl start flowpos-api flowpos-mcp` (последний шаг заново включает RLS и права рабочей роли).
- Бэкап и восстановление делаются под владельцем: под рабочей ролью `pg_dump` отказывается выгружать таблицы с RLS.
- Проверено 23.10.2026 на тестовой базе: дамп восстанавливается в пустую БД, число проводок, ЭСФ и организаций совпадает, триггеры неизменяемости на месте.
- **Рекомендация:** копировать `shared/backups` на второй сервер или в облако, иначе при потере диска пропадут и бэкапы.

## Безопасность (что сделано)
- API в боевом режиме **не запускается** без `JWT_SECRET`, `ESF_SIGNING_SECRET` и `MFA_SECRET_KEY` (все ≥ 32 символов), `DATABASE_URL` и `CORS_ORIGIN`. На уже установленном сервере `ESF_SIGNING_SECRET` и `MFA_SECRET_KEY` нужно **дописать вручную** в `/opt/flowpos/shared/api.env` до обновления (`openssl rand -hex 32` для каждого). `MFA_SECRET_KEY` после того, как пользователи подключили второй фактор, не менять.
- Привилегированные операции (пользователи и роли, подключения 1С, учётная политика, закрытие/переоткрытие периода) в боевом режиме требуют сессию, подтверждённую вторым фактором (FP-008). Отключить на время — `MFA_ENFORCE=0` в `api.env`.
- После обновления с FP-008 все пользователи входят заново (сессии на сервере, access-токен — 15 минут).
- **FP-009 — две роли БД.** API и воркеры работают под `flowpos_app` (без `BYPASSRLS`: изоляция клиентов в самой БД — RLS), миграции и бэкапы — под владельцем `flowpos` (`BYPASSRLS`). Новый сервер `install.sh` настраивает сам. **На уже установленном сервере до выкладки** (от `postgres`): `alter role flowpos bypassrls; create role flowpos_app login password '<пароль>' nosuperuser nobypassrls nocreatedb nocreaterole;`, затем в `api.env`: `MIGRATION_DATABASE_URL` — прежний адрес с `flowpos`, `DATABASE_URL` — тот же адрес с `flowpos_app`. Без этого выкладка остановится (`MIGRATION_DATABASE_URL` не задан или у роли миграций нет `BYPASSRLS`). Раньше был запасной общеизвестный ключ `flowpos-secret`, и токены можно было подделать.
- **FP-022 — мониторинг.** На уже установленном сервере дописать в `api.env` `OPS_METRICS_TOKEN=$(openssl rand -hex 32)` (без него метрик нет — 404) и при желании `OPS_ALERT_WEBHOOK_URL`. Prometheus собирает `http://127.0.0.1:3000/api/v1/ops/metrics` с этим токеном (через nginx эндпоинт закрыт), правила — `deploy/monitoring/flowpos-esf.rules.yml`, действия — `docs/erp/runbooks/ESF.md`. Схема: колонки `audit_log.trace_id`, `esf_settings.sync_*`, таблица `ops_alerts` — добавляются обычным `db push` при выкладке. Логи в бою без debug; `LOG_DEBUG=1` — включить строки каждого вызова ИС ЭСФ.
- **FP-024 — карантин входящих ЭСФ.** Новых настроек нет. Схема: таблица `esf_inbound_quarantine` и уникальность «номер+дата» входящих теперь в пределах продавца — индекс заранее создаёт `sql/pre/050_fp024_inbound_seller_unique.sql`, поэтому `db push` проходит без `--accept-data-loss`. После `db push` `sql/060_fp024_quarantine_backfill.sql` переносит неразобранные входящие из журнала FP-022 в карантин (идемпотентно). Разбор — вкладка «Карантин» на экране ЭСФ, действия — `docs/erp/runbooks/ESF.md#esf-quarantine`.
- **FP-025 — каталог.** Новых настроек нет. Схема: таблицы `catalog_settings`, `product_versions`, `external_mappings`, столбцы штрихкодов (коэффициент упаковки, источник), `products.plu`/`variant_key`; уникальность штрихкода — в пределах клиента. Индексы заранее создаёт `sql/pre/060_fp025_catalog_uniques.sql` (db push без `--accept-data-loss`); триггеры версий, сопоставлений и переноса старого поля штрихкода, а также перенос существующих данных — `sql/070_fp025_catalog.sql`. Весовые штрихкоды по умолчанию выключены — включаются в «Номенклатура → Весовые штрихкоды».
- **FP-026 — контрагенты и договоры.** Новых настроек нет. Договор теперь принадлежит организации: `sql/pre/070_fp026_contract_org.sql` до `db push` заполняет `contracts.organization_id` существующих договоров однозначно; если для договора организацию определить нельзя (общий контрагент, несколько организаций, документов нет) или номера договоров повторяются — **выкладка остановится с перечнем**: укажите `organization_id` вручную и повторите. Новые таблицы адресов и счетов контрагентов создаёт `db push`.
- **FP-027 — цены и скидки.** Новых настроек нет. Новые таблицы (`price_lists`, `price_list_items`, `discount_rules`, `pricing_settings`, `pricing_snapshots`) создаёт `db push`; `sql/080_fp027_pricing.sql` запрещает изменение и удаление снимков цен. Кассы получают правила через `GET /api/v1/pricing/snapshots/latest` (право `catalog.read`).
- **FP-028 — версии документов.** Новых настроек нет. `db push` добавляет `documents.version/posted_version`, `acc_documents.posted_version`, хэш версий, таблицы `document_versions` и `document_links`; `sql/090_fp028_documents.sql` ставит защиту проведённого содержимого, неизменяемость истории и триггеры графа, переносит существующие связи. **Внимание интеграциям:** изменение проведённого документа «на месте» теперь отклоняется БД (`DOC_POSTED_IMMUTABLE`) — обмен должен записывать исправление новой версией (`version + 1`); повторное проведение — 409 `DOC_ALREADY_POSTED` (повтор запроса — через `Idempotency-Key`); изменение торгового документа требует `expectedVersion`.
- **FP-029 — согласования.** Новых настроек нет; таблицы `approval_policies`, `approvals` создаёт `db push`. Новое право `acc.doc.approve` (владелец, администратор, главный бухгалтер). Пока правил согласования нет — проведение работает как раньше; правила включаются в «Бухгалтерия → Согласования → Правила».
- **FP-030 — журнал складских движений.** Новых настроек нет. `db push` создаёт `stock_movements` и поля приёмки в `document_lines`; `sql/100_fp030_stock_ledger.sql` сливает дубли строк остатка без ячейки (если были), ставит уникальность «одна строка на товар и склад без ячейки», записывает текущий остаток одним движением `OPENING` (источник `BACKFILL`) и включает защиту: **количество в `stock` меняется только вставкой движения** (прямая запись — ошибка БД `STOCK_LEDGER_ONLY`), движения неизменяемы (`ACC_IMMUTABLE`). **Внимание интеграциям и ручным правкам:** остаток нельзя «поправить» UPDATE-ом — только документом (оприходование/списание) или движением с источником. Удаление данных клиента целиком — ролью миграций с `SET LOCAL flowpos.stock_maintenance = 'on'` (рабочая роль так не может). Проверка после выкладки: `GET /api/v1/accounting/stock-movements/check` → `ok: true`. **Откат на релиз до FP-030** (схема назад не откатывается): старый код пишет остаток напрямую и получит `STOCK_LEDGER_ONLY` — после отката снимите защиту ролью миграций: `DROP TRIGGER IF EXISTS fp_stock_guard_trg ON stock; DROP TRIGGER IF EXISTS fp_stock_movements_apply_trg ON stock_movements;` (при повторной выкладке FP-030 `sql/100` вернёт её и допишет разницу движением `BACKFILL`).
- **FP-031 — доп. расходы и метод периода.** Новых настроек нет. `db push` добавляет тип документа `LANDED_COST`; `sql/020` разрешает количество 0 в `acc_stock_moves` только для доп. расходов. **Внимание:** метод оценки теперь берётся на 1-е число месяца — если в политике есть версия с середины месяца, она начнёт действовать со следующего месяца (себестоимость этого месяца при пересчёте может измениться); смена метода — только с 1-го числа открытого месяца.
- **FP-032 — резервы, перемещение в два этапа, ячейки.** Новых настроек нет. `sql/pre/080` — ключ ячейки «склад + ячейка» до `db push`; `db push` — таблица `stock_reservations`, `stores.is_transit`, `bins.is_active`, ячейки в строках документов; `sql/110` — триггеры резервов (свободное под блокировкой), `stock.reserved` приводится к сумме резервов (до FP-032 его никто не вёл — будет 0). **Внимание интеграциям:** `stock.reserved` больше нельзя писать напрямую (`STOCK_LEDGER_ONLY`) — резерв только через резервы заказа. Склад «В пути» создаётся автоматически при первом перемещении в два этапа.
- **FP-033 — инвентаризация, причины, партии.** Новых настроек нет. `db push` — партия/срок/учётное в строках документов и журнале, флаги партионного учёта у товаров; `sql/120` — остаток партии не уходит в минус. **Внимание:** списание (LOSS) из документов учёта теперь требует причину; инвентаризация с расхождениями проводится только после согласования (встроенное правило, можно переопределить правилом организации на INVENTORY); старые проведённые инвентаризации (без учётного количества) остаются без последствий.
- **FP-034 — заказ, отгрузка, возврат.** Схема не меняется. **Внимание пользователям и интеграциям:** возврат покупателя (`SALES_RETURN`/`RETAIL_RETURN`) из документов учёта — только на основании реализации/чека или явно `noBasis` + `returnReason`; цены отгрузки по заказу и возврата берутся из основания; заказ без цены получает цену из прайс-листов (нет цены — ошибка).
- **FP-035 — потребность, бюджет закупок, возврат поставщику.** Новых настроек нет; `db push` — таблицы `replenishment_rules`, `purchase_budgets`. **Внимание:** заказ поставщику проводится только с ценами; при заданном бюджете месяца заказ сверх него — после согласования; возврат поставщику проводится только с причиной и (как правило) по поступлению.
- Swagger в бою выключен (`SWAGGER_ENABLED=1` — включить временно).
- API и MCP слушают только 127.0.0.1, снаружи доступ только через nginx с TLS.
- nginx ограничивает частоту входа (10/мин с IP) и запросов к API, ставит HSTS и запрет встраивания в чужие сайты.
- Службы работают от пользователя `flowpos` с изоляцией systemd. Файлы с секретами — права 600.
- В архив релиза не попадают `.env`, ключи и состояние MCP: это проверяется при сборке.

## Публикация по домену (HTTPS)

`sudo bash deploy/scripts/public-domain.sh flowpos.kz 192.168.2.0/24` — nginx для домена (проверка Let's Encrypt и
перенаправление на HTTPS), брандмауэр 80/443 для всех, сертификат Let's Encrypt (без e-mail; продление — таймер certbot с
перезагрузкой nginx), HTTPS-сайт (API, без Swagger и метрик снаружи), fail2ban на перебор входа и сканеры; доступ по IP
без домена — только из локальной сети, чужие имена на 443 — сброс соединения; `CORS_ORIGIN=https://домен`. Повторный
запуск безопасен. На роутере: пробросить TCP 80 и 443 на сервер (веб-панель роутера — не на внешнем адресе).

Сброс пароля пользователя: `NEW_PASSWORD='…' node deploy/scripts/reset-password.mjs --email …` (из каталога релиза,
с переменными из `api.env`): пароль только из переменной окружения, сессии отзываются, запись в журнал аудита.
