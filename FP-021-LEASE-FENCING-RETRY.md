# FP-021: Аренда задач, fencing, повторы и DLQ

**Status:** ✅ DONE_LOCAL — для очереди outbox → 1С (единственная durable-очередь сейчас); не выкладывалось
**Date:** 2026-10-30
**Backlog:** Platform · P0 · deps FP-009 · acceptance: *Stale worker не подтверждает чужой lease; jitter/Retry-After; unsafe stage не retry*

Ночная версия FP-021 (`eb56569`) откачена 30.10 (`5f86019`). Это новая реализация.

## Было

- Outbox разбирали **два** потребителя без координации: `push-worker` и Bull-процессор в API (вторым путём, через
  другой клиент 1С) — риск двойной отправки.
- `push-worker`: `FOR UPDATE SKIP LOCKED` держал блокировку только на время выборки; аренды не было; любые 5xx и
  таймауты повторялись вслепую (повтор мог создать дубль в 1С); задержки — фиксированная лестница без jitter;
  `Retry-After` не учитывался.
- Скрытые ошибки (код ни разу не работал на реальных данных): `id = ANY(…::uuid[])` при текстовом `id` (FP-009);
  поля сырого SQL читались как camelCase (`entry.localId`, `entry.idempotencyKey` — `undefined`): ключ
  идемпотентности не передавался, GUID записывался по пустому `id`.

## Стало

- **Один потребитель** — `push-worker`; Bull-процессор удалён (`SyncService.enqueue` его единственный источник
  нигде не вызывался).
- **Аренда:** захват одним `UPDATE … FROM (SELECT … FOR UPDATE SKIP LOCKED)`: `lease_owner`, `lease_until` (5 мин),
  `fencing_version + 1`, `attempts + 1`, `stage = CLAIMED`.
- **Fencing:** любое подтверждение (DONE + запись GUID — одной транзакцией; повтор; UNKNOWN; DLQ) — условное
  `id + lease_owner + fencing_version + status = SENDING`. Перед сетью `stage = SENDING` — тоже условно, поэтому
  воркер с перешедшей арендой **не отправляет и не подтверждает**.
- **Истёкшая аренда:** на `CLAIMED` (до сети не дошли) — запись снова берётся; на `SENDING` — `UNKNOWN`
  («истёкший lease не доказывает неотправку»), без автоматического повтора.
- **Решение по ошибке** (`apps/push-worker/src/modules/push/retry-policy.ts`):
  - соединение не установлено (`ECONNREFUSED`, `ENOTFOUND`…) — повтор;
  - `429`, `503` с `Retry-After` — повтор не раньше указанного;
  - таймаут/обрыв после соединения и `5xx` — **UNKNOWN** (1С могла принять запрос), если идемпотентность 1С по
    ключу не подтверждена (`ONEC_IDEMPOTENCY_CONFIRMED=1` — только после проверки на реальной базе; и тогда только
    для операций, отправляющих ключ: создание, обновление документа; проведение/удаление — всё равно UNKNOWN);
  - `4xx` — DLQ (`DEAD`) сразу; `409` с GUID — успех; 12 попыток — DLQ.
- **Задержка:** экспонента 60 с·2^(n−1) с полным jitter (равномерно до потолка, потолок 12 ч), не меньше
  `Retry-After` (секунды или HTTP-дата, не больше суток) и не меньше 1 с.
- **Оператор:** `POST /sync/outbox/:id/requeue` — из `UNKNOWN`/`DEAD`/`ERROR` обратно в очередь с причиной
  (что проверено в 1С), право `sync.manage`, MFA, запись `OUTBOX_REQUEUE` в журнале.
