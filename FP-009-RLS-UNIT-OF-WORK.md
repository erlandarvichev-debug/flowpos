## Роли

| Роль | Кто | Права |
|---|---|---|
| `flowpos` | миграции (`sql/pre`, `db push`, `sql/*`), бэкап/восстановление | владелец таблиц, `BYPASSRLS` (FORCE RLS действует и на владельца) |
| `flowpos_app` | API и все воркеры | `LOGIN NOSUPERUSER NOBYPASSRLS`, только `SELECT/INSERT/UPDATE/DELETE`; DDL, отключение RLS и политик — запрещены |

`api.env`: `DATABASE_URL` — рабочая роль, `MIGRATION_DATABASE_URL` — владелец. `install.sh` создаёт обе роли,
`deploy.sh` мигрирует под владельцем (без `MIGRATION_DATABASE_URL` — стоп), `backup.sh` — под владельцем
(проверено: под рабочей ролью `pg_dump` отказывается выгружать таблицы с RLS). `sql/040` останавливает выкладку,
если у роли миграций нет `BYPASSRLS` (иначе `sql/pre` молча не увидит данных) или у рабочей роли он есть.

## RLS (`packages/db/prisma/sql/040_fp009_rls.sql`, FORCE на 93 из 100 таблиц)

- с `tenant_id` (22) — строки текущего клиента; `tenants` — сам клиент;
- с `organization_id` без `tenant_id` (43) — `organization_id IN (SELECT id FROM organizations)`: таблица организаций сама
  под RLS, подзапрос видит только своего клиента; общий план счетов (`acc_accounts` без организации) читают все;
- дочерние (17: версии документов, смены и кассовые операции, отметки времени, журналы обмена…) — через родителя;
- служебные (11: состояния OIDC, курсор автопилота, витрины, неиспользуемые gig/marketplace) — только системный режим;
- глобальные справочники без RLS (7): план счетов (`acc_charts`), валюты, курсы, ставки НДС, роли/права старого модуля.
- Новая таблица, не отнесённая ни к одной группе, останавливает выкладку. Политики переживают `db push` (проверено).

## Единица работы: контекст клиента в каждой транзакции

- `apps/api/src/common/db-context.ts` — AsyncLocalStorage; `DbContextMiddleware` открывает пустой контекст на запрос,
  `JwtStrategy` после проверки сессии привязывает к нему клиента.
- `PrismaService` (тот же класс для DI): запрос модели и сырой SQL — транзакция `set_config(flowpos.tenant_id, …, true)`
  + запрос; `$transaction(fn)` — контекст первым оператором той же транзакции; значения transaction-local — пул чистый.
- **Нет контекста — строк нет** (fail-closed). Системный режим — только явно (`runAsSystem`): вход, обновление
  токена, MFA-вход, OIDC до определения клиента; развёртывание общего плана счетов; перечни в фоновых задачах.
- Фоновые задачи: перечень — системно, обработка — `runAsTenant` клиента документа/организации/подключения
  (автопилот, ЭСФ, 1С, МойСклад, отправка в 1С); витрины аналитики — системно.
- Атомарность команд: торговые документы, проводки, ЭСФ — уже в одной транзакции; доделано: внесение/выемка в кассе
  (сумма смены и операция), смена пароля/отключение и отзыв сессий.

## Outbox

- `outbox.tenant_id` — по умолчанию из `SET LOCAL` транзакции, где записан агрегат; сервисы передают его и явно.
  `sql/pre/040` заполняет существующие записи (документ, подключение, единственный клиент; иначе — стоп).
- Запись outbox — в той же транзакции, что и документ: откат команды откатывает и её; другим соединениям она видна
  только после commit.
- `push-worker` отправляет запись только в подключение организации **того же клиента** (раньше любой
  `connection_id`). Попутно исправлено: `id = ANY(…::uuid[])` при текстовом `id` (сравнение не определено).

## Проверка

`apps/api/test/rls.int-spec.ts` — 14 тестов на рабочей роли: атрибуты роли и запрет DDL/отключения RLS; покрытие RLS;
без контекста — 0 строк; клиент не видит, не меняет, не удаляет чужое и не вставляет в чужого клиента (товары,
документы, проводки через организацию, смены через родителя, outbox); составной FK в системном режиме; **сбой
в середине команды откатывает документ, строки и outbox**; **outbox не виден до commit** и получает клиента из
транзакции; воркер 1С без контекста не видит подключений и не может писать в другого клиента; отправка не уходит
в подключение другого клиента. Мутация (политика `USING (true)` на товарах) роняет 3 теста.

Все HTTP-наборы (FP-007/008: e2e, права, MFA, OIDC, сессии, зарплата) теперь идут под рабочей ролью — с RLS.
Итого: интеграционные 148 + 1 skip, юнит 102/102, ЭСФ 230/230, все сборки — exit 0.

## Ограничения и не сделано

- **RLS не защищает от скомпрометированного сервера**: рабочая роль сама выставляет `flowpos.system`/`tenant_id`
  (как и в ТЗ: «RLS cannot protect a compromised server that can choose any trusted context»). Она защищает от
  ошибки фильтра в коде.
- Каждый запрос вне `$transaction` — короткая транзакция из двух операторов (дополнительные round-trip'ы); на
  нагрузке пилота не измерялось.
- Прямые тесты сервисов (без HTTP) идут под владельцем; RLS проверяется HTTP-наборами и `rls.int-spec.ts`.
- `push-worker`: `FOR UPDATE SKIP LOCKED` освобождается сразу после выборки (как и раньше) — аренда/fencing задач — FP-021.
  `sync-queue.processor` помечает `DONE` записи без подключения (старый пробел, см. FP-007).
- Глобальные справочники рабочая роль может изменять (нужно для развёртывания плана счетов при старте).
- Локально роль `flowpos` получила `BYPASSRLS`, создана `flowpos_app` (пароль `flowpos_app_dev` — только для разработки).
